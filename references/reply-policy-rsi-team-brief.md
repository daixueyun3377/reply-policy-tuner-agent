# reply-policy RSI 初版沟通稿

这篇用于团队第一次对齐：我们为什么要做 reply-policy RSI（递归式自我改进）、第一阶段做什么、边界在哪里、后续会演进到什么程度。

## 1. 要解决的问题

Agent（智能体）本身不是稀缺能力，真正的产品竞争点是：每个运营或运营团队的回复策略，能不能基于真实反馈持续变好。

当前 `reply-policy-tuner-agent` 已经能安全改策略：读取策略、校验 Patch（补丁）、预览、评估、确认、写入。下一步要补的是策略优化的前半段：真实问题从哪里来，如何沉淀成样本，如何生成可评估的优化建议。

## 2. 核心闭环

我们不做“让 Agent 自己随便改自己”，而是做一个可控闭环。

<whiteboard type="mermaid">

  A["发现问题"] --> B["沉淀样本"]
  B --> C["生成建议"]
  C --> D["转成 Patch"]
  D --> E["评估效果"]
  E --> F["人工确认发布"]

阶段 1 仍然保留 human-in-the-loop（人在回路）：系统自动发现问题和提出建议，发布必须经过评估和人工确认。

## 3. 四个组件与数据流

| 组件 | 主要职责 |
|------|----------|
| collector | 收集人工改写、人工接管、明确负反馈，以及高置信成功样本 |
| RAS | 存样本、聚合同类问题、生成 Proposal（优化建议） |
| tuner | 将建议转 Patch，继续走 validate / preview / evaluate / update |
| roll-core | 串联用户确认、多 Agent 调用和异常分支 |

## 4. 阶段路线

最终目标不是让 Agent 自动乱改策略，而是让每个 tenantId 的回复策略基于真实业务反馈持续自优化：低风险优化可以自动闭环，高风险优化保留人工确认和安全门禁。

## 5. 阶段 1：做什么 / 不做什么

| 做什么 | 不做什么 |
|--------|----------|
| 收集人工改写、带原因接管、明确负反馈 | 不自动发布策略 |
| 同时沉淀高置信成功样本 | 不根据单条失败样本立刻改策略 |
| RAS 聚合同类问题，生成带证据的建议 | 不把候选人沉默、转化下降直接当失败样本 |
| 用户在 tuner 里采纳、修改、忽略或暂缓建议 | 不改 reply-policy schema，只优化 policy values |
| 被采纳的建议继续走现有评估和发布门禁 | 不让 collector 直接写策略 |

隐私与数据留存是前置约束：样本入库前必须脱敏，跨租户只共享抽象模式，不共享候选人原始对话；具体留存期限需要和合规一起确认。

## 6. 阶段 1 关键设计

### 6.1 评估口径

“持续变好”不能只靠主观判断。阶段 1 就要定义 Evaluation Contract（评估契约）。

| 问题 | 口径 |
|------|------|
| 离线评估靠什么 | 失败样本 + 成功样本 + 系统回归样本 |
| 怎么证明修复 | 候选策略在失败样本上提升修复率 |
| 怎么防止回归 | 候选策略不能破坏成功样本和系统回归样本 |
| 主指标 | 修复率、回归率、合规违规数、与人工改写的语义一致度 |

Replay Evaluation（回放评估）的前提是采集时保存必要输入快照，例如候选人消息、对话上下文、Agent 原回复、最终发送回复和当时的 policyVersion。

### 6.2 RAS 生成建议的关键机制

RAS 真正要做的是“从零散反馈中识别系统性策略问题”，不是把每次人工改写都当成策略失败。

| 机制 | 说明 |
|------|------|
| 聚类维度 | failureType（失败类型）、stage（阶段）、policyPath（策略路径）、语义相似度 |
| 阈值 | 同时看绝对数量和流量占比，避免大 tenant 过敏、小 tenant 永远触发不了 |
| 归因过滤 | 人工改写不等于策略错了，必须结合 diff、原因和重复性判断 |
| 小租户冷启动 | 样本不足时可参考跨租户共性问题，但发布仍按 tenantId 独立评估 |
| 置信度 | 建议附带证据样本数、时间跨度、流量占比、影响面预估 |

### 6.3 追踪和回滚

- 每个建议记录 evidence（证据）、policyVersion、suggestedPatch。
- 每次发布记录 proposalId、评估结果、发布人、发布时间。
- 建议状态机：生成、待审、采纳、修改、忽略、暂缓、已发布、已回滚、关闭。
- 发布后继续观察人工改写率、接管率、负反馈率、事实错误率。
- 出现明显变差时生成 rollback candidate（回滚候选），仍由 tuner 走确认和发布门禁。

线上归因需要谨慎：低流量 tenant 只能做定性观察，高流量 tenant 后续可考虑 Control Group（对照组）或灰度对比。

## 7. 用户感知与价值

| 以前 | 以后 |
|------|------|
| 用户自己诊断“我想怎么改策略” | 系统提示“最近发现哪些问题” |
| 上层 Agent 生成 Patch | 系统展示证据样本和优化建议 |
| 用户只能凭经验判断是否要改 | 用户选择采纳、修改、忽略或暂缓 |
| tuner 评估和发布 | tuner 继续评估和发布，门禁不变 |

预期价值：

- 策略优化从拍脑袋变成 evidence-driven optimization（证据驱动优化）。
- 每个 tenantId 可以形成自己的策略演进路径。
- 现有安全门禁不变，降低自动优化带来的发布风险。

## 8. 一句话总结

reply-policy RSI 的最终目标，是让每个运营或运营团队的回复策略基于真实反馈持续变好；阶段 1 先从“自动发现问题并提出可审计建议”开始，再逐步演进到低风险优化的自动闭环。
