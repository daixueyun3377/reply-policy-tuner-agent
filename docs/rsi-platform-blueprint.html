Recursive Self-Improvement

把用户反馈、评估失败和发布效果变成可审计的持续优化闭环

RSI 不是让模型自动乱改系统，而是一个跨 Agent（智能体）的优化平台。公共 Backend Core（后端核心服务）负责证据链和生命周期，Optimizer（优化器）负责发现和建议，业务 Adapter（适配器）负责语义映射，业务 Agent（智能体）负责评估和发布门禁。

公共平台事件、样本、问题、候选、评估、发布、观察。
通用优化聚类、归因、候选生成、样本选择、效果分析。
业务适配reply-policy、企业微信回复、nl2sql 各自定义语义。
受控发布Candidate-only（只生成候选、不自动发布），发布回到各 Agent（智能体）的门禁。

1. RSI 整体愿景

RSI 的目标是让产品具备持续学习能力：用户用得越多，系统越知道哪里不好；系统越知道哪里不好，越能提出可验证的优化；优化经过评估和发布后，真实效果再回流，形成下一轮优化。

输入
真实会话、运营反馈、人工改写、评估失败、Judge 告警、SQL 执行失败、发布后指标。
智能分析
失败聚类、问题归因、候选优化生成、评估样本选择、发布后效果分析。
业务门禁
reply-policy 走 RAS validate / preview / evaluate / update（校验 / 预览 / 评估 / 写入）；NL2SQL 走 SQL 执行和安全评估；企业微信回复走话术质量和事实校验。
输出
可解释的候选优化、回归样本、发布记录、效果观察、回滚建议。

产品竞争力提升

质量提升回复更贴合业务，SQL 正确率更高，高频失败进入回归集。
效率提升系统自动整理问题和候选优化，减少重复人工调参。
数据护城河真实反馈、改写、失败和发布效果沉淀为长期优化资产。

2. 架构设计

业务 Agent（Business Agents）
回复策略调优 Agent 企业微信回复 Agent NL2SQL Agent
事件接入（Event Ingestion）

REST API、Webhook（网页回调）、RAS Forwarding（RAS 转发）、Agent SDK（智能体开发包）。事件写入必须幂等，失败不能阻塞主业务流程。

RSI 后端核心服务（RSI Backend Core）
Event（事件） Sample（样本） Problem（问题归因） Candidate（候选优化） Evaluation（评估记录） Release（发布记录） Observation（发布后观察）
RSI 优化服务（RSI Optimizer Service）

样本聚类、问题归因、候选生成、评估样本选择、发布后效果分析、报告生成。

业务适配器（Business Adapters）

将通用优化结果映射成对应业务可评估、可发布的 Candidate（候选优化）。

评估与发布门禁（Evaluation and Publish Gates）

业务 Agent（智能体）保留最终评估与发布门禁。RSI 不直接发布。

推荐技术栈

层级推荐说明
Backend Core（后端核心服务）TypeScript + Node.js + NestJS 或 FastifyRAS 已使用 Node，优先沿用 RAS 当前框架、鉴权、日志、配置和部署方式。
Optimizer Worker（优化任务进程）TypeScript + BullMQ / Redis Stream第一阶段用 Node Worker（Node 任务进程），后续复杂 Embedding（向量化）、聚类、ML Pipeline（机器学习流水线）可拆 Python Worker（Python 任务进程）。
Database（数据库）PostgreSQL + JSONB结构字段用于查询，JSONB（PostgreSQL 的 JSON 存储类型）存不同业务 Payload（业务载荷）。
Vector（向量检索）pgvector 起步pgvector（PostgreSQL 向量检索扩展）在样本相似检索需要时引入。
Queue（任务队列）Redis + BullMQBullMQ（基于 Redis 的 Node.js 任务队列）用于异步处理事件和 Optimizer Job（优化任务）；已有 Kafka（分布式消息队列）时可复用 Kafka。
LLM（大语言模型）用于归因、候选草稿、报告LLM 输出必须结构化校验，不能直接发布。
Observability（可观测性）traceId（链路追踪 ID）、eventId（事件 ID）、candidateId（候选优化 ID）、audit log（审计日志）保证可追溯、可排障、可回滚。
架构建议：第一期做 TypeScript/Node 模块化单体 + BullMQ Worker（任务进程）+ PostgreSQL + Redis，不要一开始拆复杂微服务。后续再拆 Optimizer Service（优化服务）、Adapter Worker（适配器任务进程）或 Report Service（报告服务）。

RAS 与 RSI 的关系

推荐：
tuner agent（调优智能体） → RAS
RAS → RSI backend

短期备选：
tuner agent（调优智能体） → RAS
tuner agent（调优智能体） → RSI backend（RSI 后端） async fire-and-forget（异步上报，不阻塞主流程）

reply-policy 场景中，RAS 更接近策略、评估和发布事实源。优先让 RAS 转发事件给 RSI backend，tuner 不做长期数据仓库。

3. 自我优化内容

通用优化能力

失败样本聚类发现高频失败模式，如语气偏冷、SQL 漏时间条件。
问题归因区分策略问题、事实证据问题、Prompt（提示词）问题、Schema Linking（数据结构关联）问题。
候选生成生成 Policy Patch（策略补丁）、Prompt Patch（提示词补丁）、Few-shot（少样本示例）、Schema Hint（数据结构提示）。
样本选择自动选择 Primary Cases（主样本），补充 Regression Cases（回归样本）。
效果分析比较发布前后指标，发现收益、回归或无效优化。
报告生成输出周报、问题趋势和优化建议。

候选优化（Candidate）生命周期

proposed（已提出）
→ ready_for_evaluation（待评估）
→ evaluating（评估中）
→ evaluated_passed / evaluated_failed（评估通过 / 评估失败）
→ accepted / rejected（已接受 / 已拒绝）
→ released（已发布）
→ observed_positive / observed_negative / rollback_suggested（观察为正向 / 观察为负向 / 建议回滚）

业务优化示例

业务自我优化内容典型 candidate
reply-policy语气、CTA、阶段策略、事实门禁、输出保护、回归样本policy_patch
企业微信回复Prompt（提示词）、模板、首轮承接、追问策略、CTA 时机、事实表达prompt_patch（提示词补丁） / template_patch（模板补丁）
NL2SQLFew-shot（少样本示例）、Schema Hint（数据结构提示）、Join Rule（关联规则）、Metric Definition（指标定义）、SQL Guardrail（SQL 安全护栏）few_shot_case（少样本用例） / schema_hint（数据结构提示）
边界：Optimizer（优化器）只提出候选建议；真正的业务变更必须回到对应 Agent（智能体）的评估和发布门禁。

4. 风险与防护

风险说明防护策略
过拟合只对触发样本有效，泛化差。训练/评估样本分离、固定回归集、灰度、发布后观察。
数据污染错误反馈或低质量改写进入优化链路。来源标记、置信度、人工审核、异常过滤。
奖励黑客迎合 Judge 而不是真实质量。frozen judge、多目标评估、线上指标、人工抽检。
安全旁路候选优化放宽事实门禁或 SQL Guardrail（SQL 安全护栏）。高危检测、强门禁、禁止自动发布。
归因错误把事实库缺失误判为策略问题。区分 policy issue 与 data/evidence issue。
指标误归因发布后变化不是 candidate 导致。灰度、对照组、置信度、分层分析。
隐私泄露样本包含敏感信息。脱敏、租户隔离、权限、保留周期。
成本失控LLM 分析和评估调用过多。分层采样、批处理、缓存、预算控制。
状态不一致RAS、RSI、Agent（智能体）记录对不上。traceId（链路追踪 ID）、eventId（事件 ID）、幂等键、版本号。
自动化过度系统绕过人工和门禁直接发布。Candidate-only（只生成候选、不自动发布），发布回业务 Agent（智能体）。
schema 膨胀每个问题都新增字段。第一层优先，第二层走 schema proposal。
跨业务污染NL2SQL 优化逻辑影响 reply-policy。公共生命周期，业务 Adapter（适配器）分离。
回滚困难发布后变差但找不到来源。Release（发布记录）、Affected Paths（受影响路径）、Rollback Plan（回滚方案）。

防过拟合机制

样本隔离生成 candidate 和评估 candidate 使用不同样本。
固定回归集每个 Agent（智能体）维护 Frozen Regression Suite（冻结回归测试套件）。
小步优化一次 candidate 尽量只改少量对象。
灰度发布按 tenant、场景或流量比例发布。
发布后观察用真实指标确认收益和回归。
多目标评估同时看质量、安全、事实、转化和成本。

5. 任务拆分与路线图

Phase 0

概念对齐与数据盘点

确认三个 Agent（智能体）的 RSI 范围、数据来源、发布门禁和 RAS 当前存储能力。输出数据盘点表、接入边界和 MVP（最小可行产品）事件清单。

Phase 1

RSI backend core MVP

建立 Events（事件）、Samples（样本）、Problems（问题归因）、Candidates（候选优化）、Evaluations（评估记录）、Releases（发布记录）、Observations（发布后观察），支持幂等写入、查询、权限和审计。

Phase 2

接入 reply-policy-tuner / RAS

上报 Validate（校验）、Preview（预览）、Evaluate（评估）、Update / Release（写入 / 发布）事件，从 Evaluate 失败生成 Problem（问题归因）和 Policy Patch Candidate（策略补丁候选）。

Phase 3

optimizer service v1

实现规则型归因、LLM（大语言模型）Problem Report（问题报告）草稿、失败样本聚类、Candidate（候选优化）草稿、Regression Case（回归样本）推荐和优化报告。

Phase 4

接入 NL2SQL Agent（智能体）

上报 SQL 生成和执行结果，归因 SQL 错误，生成 Few-shot（少样本示例）、Schema Hint（数据结构提示）或 Prompt Rule Candidate（提示词规则候选）。

Phase 5

接入企业微信回复 Agent（智能体）

上报模型回复、人工改写、用户反馈和人工接管，生成 Prompt / Template / Strategy Candidate（提示词 / 模板 / 策略候选）。

Phase 6

治理、灰度与平台化

建设 dashboard、灰度、回滚、成本治理、安全审批和周期性优化报告。

6. 决策建议

问题推荐决策
RSI backend core 用什么语言？TypeScript / Node，并优先沿用 RAS 当前框架。
第一条链路接谁？先接 reply-policy，因为已有完整 evaluate/update 门禁。
事件由谁上报？reply-policy 优先由 RAS 转发；短期可 Agent（智能体）异步上报。
第一阶段是否自动发布？不自动发布，只生成 candidate。
数据库怎么选？PostgreSQL + JSONB（JSON 存储类型）起步，必要时加 pgvector（向量检索扩展）。
队列怎么选？Redis + BullMQ 起步，已有 Kafka 可复用。
Adapter（适配器）谁维护？各业务 Owner（负责人）维护，公共平台提供生命周期和接口。
底线：RSI Optimizer（优化器）生成的是候选优化，不是发布指令。任何业务变更都必须回到对应 Agent（智能体）的评估、确认和发布门禁。
